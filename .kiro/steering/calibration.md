# 标定结论、被拒方案与已知悬案

## 最高原则：阈值必须实测，不得凭空设定

这是本项目反复确立的纪律。任何感知参数都必须来自 `captures/` 里真实帧的测量
（`tools/calibrate.py` / `tools/benchmark_vision.py`），并把测量结果写进注释或本文档。

**"调高阈值让它通过"等于凭空编造证据，是被明确拒绝的做法。**

下面每一条都是实测结论。**不要在没有新证据的情况下修改它们**，尤其不要"顺手优化"
那些看起来像是被禁用或被保守设置的项——它们是有理由的。

## 已标定参数

| 参数 | 取值 | 实测依据 |
| --- | --- | --- |
| `reference_size` | `(1024, 768)` | 游戏内分辨率，所有配置以此为基准换算 |
| `match_threshold` | `0.75` | 分数分布 p5=0.53 / p50=0.80 / p95=0.89；即便放宽到 0.50，24 帧内零假阳性 |
| `nms_distance` | `30` | 实测真实牌子间距下界 38.6px，取 30 留余量又不合并相邻牌 |
| `scale_steps` | `(0.97, 1.0, 1.03)` | 5 档与 3 档找到完全相同的 73 个目标但慢 3 倍；1 档漏 18% |
| `match_downscale` | `0.5` | 103~108ms → 30~48ms（2.2~3.6×），漏检 1.8%，坐标漂移 2px |
| `search_region` | `None` | 见下方「被拒方案」 |
| `require_texture_below` | `False` | 见下方「被拒方案」 |
| `max_clicks_per_tick` | `3` | 只批量互不重叠的候选；`click_separation_margin=6` |
| `recheck_before_batch_click` | `True` | 批内每次点击前重新截图确认 |
| `click_cooldown` | `0.35` | 配合下方阶梯冷却 |
| `failure_cooldown_ladder` | `(1.0, 3.0, 8.0)` | 连续失败才逐级升冷却 |
| `blacklist_after_failures` | `4` | 达到次数后拉黑该位置 |
| `verify_trust_after` | `2` | 连续成功 2 次后转入抽样验证 |
| `verify_sample_every` | `8` | 抽样间隔 |
| `verify_delay` | `0.28` | 点击后回读延迟 |

## 被拒方案（不要重新引入）

**`require_texture_below=False` —— 禁用而非重调阈值。**
实测 219 个检测的探测值落在 41.8~72.4，而阈值是 12.0，拒绝率 **0%**，且手头没有负样本
可以把它和真实目标分开。既然这条规则不产生任何区分力，就诚实地禁用它。
调高阈值直到它"起作用"= 凭空编造证据，已明确拒绝。

**`search_region=None` —— 裁 playfield 是负优化。**
实测裁剪反而更慢：105~129ms vs 基线 103~108ms。原因是内存复制加上不连续视图，
抵消了搜索面积的收益。

**`match_downscale=0.4` 被拒。** 相比 0.5 只再省 13ms，但漏检从 1.8% 翻倍到 4.5%。

**平坦冷却被拒，改用阶梯冷却。** 成功点击后目标已经消失，继续等待没有任何收益；
只有在**连续失败**时才有理由拉长冷却。设计要求是：
判断连续失败一定次数之后，才考虑进入较长冷却。

**"一次识别全部然后批量点"被拒，改为迭代式。**
牌子会互相遮挡，被挡住的那些位置**未知**，必须逐层剥离：每轮点最靠前、分数最高的，
下一轮重新识别。结论：按照覆盖优先级一个一个点。
这也是为什么 `max_clicks_per_tick=3` 只批量**互不重叠**的候选。

**为 memory game 的卡面做模板被拒。** 图案种类太多。必须做**运行时相似度比较**。

**截图失败时默认允许点击被拒。** `recheck_before_batch_click` 在截图失败时返回
「目标不在」——**无证据不等于允许点击**。

## 已修复的真实 bug

留档以免重复踩：

1. **DPI 感知不一致** —— 详见 `workflow.md` 陷阱四。
2. **`_suppress_duplicates` 是 O(n²)，会卡死。**
3. **GDI 资源每帧重建** —— 改为复用。
4. **批内坐标过期** —— 前一次点击导致视角平移后，同批剩余坐标已失效。
   修法是批内每次点击前重新取证。

## 性能现状

单个金币约 **0.4~0.5 秒**（最初 2.1 秒）。三轮实机耗时分布：

```
单轮 374 / 495 / 545ms
截图 48~57ms (10~15%) ｜ 识别 39~45ms (8~10%) ｜ 点击 63~104ms (16~19%)
回读 72~179ms (19~35%) ｜ 间隔 144~165ms (30~38%)
```

回读与间隔是当前的主要成本。还想更快，但这部分若较难进步，
就先进入下一功能开发——目前已进入 memory game 阶段。

## 未解悬案：偶发误触

**根因未找到，不要假装已解决。**

现象：偶发点到建筑物 → 游戏平移视角 → 坐标过期 → 引发更多误触。

已确认的事实：

- 级联部分已修（批内重取证），但**"第一次误触为何发生"仍无解释**。
- 判断：脚本知道那个标志不是金币，依据是点击建筑物同样会导致视角平移。
  → 因此这是**点击落错位置**，不是识别错误。
- 实测：不缩放的基础上，平移画面后脚本可以正常执行。
- 多屏假设已排除（只有一块屏幕）。
- 「实验一先对后错」（Qt + raw 发送）的机制**未解释**。
- 三轮实机数据里坐标过期跳过 1/5/0 次，抽检失败 2/15、5/14、0/4，已拉黑 0。

尚未做的取证手段：回读失败时保存**标注了点击坐标的前后帧**。
目前无法区分「真误触」与「动画未播完导致回读误判」。

### 第一个有机制的候选解释：镜头平移与点击撞车

**实测补充**：拖动镜头不影响金币的坐标识别，但可能在漂移过程与点击动作
发生碰撞而导致误判（不确定）——识别没问题，**可疑的是漂移与点击的时序**。

据此把点击路径逐行核对了一遍，代码里确实留着这么一条通路，四个环节全部对得上：

1. **每轮第一次点击从不重新取证。** `_click_batch`（`bot_engine.py`）的复核写在
   `if index > 0` 里，所以 `index == 0` 那次、以及**本轮只有一个候选**时的唯一那次，
   用的是本轮开头那张帧的坐标。按实测分段（截图 48~57ms、识别 39~45ms，
   加上抖动前后的睡眠），**`WM_LBUTTONDOWN` 送达时坐标已有约 90~135ms 的年龄**，
   这段时间里没有任何东西检查过画面是否在动。
2. **`_still_present` 通过后仍然点旧坐标。** 它只回答「旧坐标 20 参考像素内还有没有
   金币」，返回 True 之后 `_click_batch` 点的依然是 `coin.center`，
   当帧检出的新中心被丢掉。**所以 20px 以内的平移既不拦也不纠**，
   再叠加 `jitter_radius=5`，实际落点可能偏离目标中心 25px。
3. **跨帧确认会跟着漂移走。** `ClickGuard.observe` 里那行 `track.point = center`
   （注释写的是"Follow small drift so an animated target keeps its identity"）
   意味着只要每帧位移 ≤ `confirm_tolerance=12` 参考像素，
   **平移中的金币会保住自己的确认计数**，不会被 `AWAITING_CONFIRMATION` 挡下。
   这是整条路径上唯一偶然具备"运动抑制"效果的机制，
   而它是**为动画精灵设计的，不是为镜头平移设计的**，带宽只有 12px/帧。
4. **平移会把误触记成成功，所以日志里看不见。** `_verify_click` 的判据是
   「被点坐标 20px 半径内还检不检得到金币」。如果这 `verify_delay=0.28` 秒里画面平移了，
   金币只是移出了旧坐标的邻域 → `still_there=False` → `register_result(target_gone=True)`
   → 失败计数清零、`_verified_streak += 1`，还推着引擎更快进入"每 8 次抽检一次"。

**第 4 条解释了为什么这个悬案一直查不出来**：在平移场景下，
取证链路本身会把这类误触判成成功。「根因未找到」与「这条通路存在」是自洽的，
不是矛盾。

**代码里早就有一半的猜测。** `ClickConfig.batch_settle_delay` 的注释写着：
`MOVE -> DOWN -> UP -> MOVE(far) -> DOWN -> UP` 在尚未处理完 UP 的输入层看来
可能像一次拖拽，而**拖拽在这个游戏里会平移镜头**，并注明"unverified as a cause
but cheap as a precaution"。把它和上面那次观察拼起来，就得到一个完整的闭环：
**脚本自己的连续点击可能被解读成拖拽 → 镜头平移 → 剩余坐标过期 → 落到景物上 →
再次平移。** 而第一次误触不需要外部原因，脚本自己就能触发。

**这仍然是假设，不是结论。** 缺的是取证。要确认或推翻它，需要两件事：

- **回读失败时保存标注了点击坐标的前后帧**（本来就在待办里，现在有了明确的判据：
  看两帧之间**整个场景**有没有位移，而不只是看那一枚金币还在不在）
- **给 `Detection` 补一个单调时钟戳或帧序号**。目前它只有类别、框、分数，
  上层**无法回答"这个坐标是基于多久以前的画面算出来的"**，
  批里第 1 个和第 3 个候选的坐标年龄可能差 200ms 以上，而代码里区分不出来

**修的方向已经清楚，而且是现成的**：memory game 那边早就确立了
「不要在东西还在动的时候取样，直接测量静止性」（`looks_stable()`，阈值 0.98，
连续两次通过）。金币这条路径上**没有任何对应物**——
检索 `core/*.py` 的 `looks_stable|motion|stationary|panning` 只命中文档字符串。
所以最合理的修法不是继续缩短那 100ms 的窗口（用 `SendMessage` 时点击何时被处理
由游戏决定，窗口缩不到零），而是**加一道"画面静止"前置门**：
画面在动就不点，等它停。这与 memory game 的结论是同一条——
**不要试图跑得比动画快，直接测量动画有没有结束。**

顺带一条：`recheck_before_batch_click` 在 `max_clicks_per_tick <= 1` 时会被
与条件整体算成 `False`。所以**把批量大小调成 1 并不会得到"更保守"的行为**，
反而是关掉了复核。改那个值之前要知道这件事。

### 更坏的一条：点到设施会强制平移**并且缩放**

**补充实测**：脚本运行时确实见过平移。点到一些设施时，视角也会被强制移动
**并且发生画面缩放**。

**缩放比平移严重得多**，因为它打的是感知层而不是坐标：

- `scale_steps = (0.97, 1.0, 1.03)` 只有 ±3% 的带宽，而它的注释已经写明
  「this band covers window-size rounding, **NOT the game's own camera zoom**.
  Zoom changes sprite size independently of window size, so detection will miss
  outside the band.」——**这是当初就写下的诚实限制，现在撞上了。**
- 平移的后果是「坐标过期」，重新截图就能纠正。
- **而且没有任何东西会把缩放恢复回去。** 代码里没有 zoom 复位逻辑，
  也没有"当前缩放是否还在标定范围内"的检查。

### 更正：缩放**不会**让金币检不到

**上面那段原来断言「缩放的后果是根本检不到，重新截图也没用」，那是错的。**
它是从 `scale_steps` 的注释推理出来的，没有实测；实机观察推翻了它。

**实测观察（两条，都由实机得到）：**

1. **金币图标不随镜头缩放改变尺寸。** 所以模板尺寸始终对得上，**缩放不影响识别**。
2. **怪兽会随缩放变大变小。**

两条合起来给出一个自洽的模型：**金币牌是屏幕空间精灵**（固定像素尺寸，任何缩放级别下
都好点，这正是休闲游戏让收集物始终可点的常见做法），**而怪兽是世界空间物体**。

**所以缩放真正改变的是可见范围,不是识别能力**：视野外的金币收不到。
这是"覆盖不全"，与原来写的"感知失效"是完全不同、也轻得多的问题。

**推论一：那条「实验一先对后错」的候选解释随之作废。** 它建立在"缩放让模板全部
偏离标定尺度"之上，而那个前提是假的。**那条悬案回到「机制未解释」状态**——
排除一个错误的解释比留着它好。真正的候选解释见下面的指针那一节。

**推论二：全屏可用，而且它验证了几何层。** 实机确认**全屏下两个功能都正常**。
全屏客户区不是 1024x768，`scale_factor` 不等于 1.0，模板被按比例缩放——
它能工作说明「一套模板适配任意窗口尺寸」这条契约在实机成立。

**但窗口尺寸缩放与游戏内镜头缩放是两件事，别混：**

```
窗口尺寸变化   改变整帧像素密度   几何层能换算       已实机验证（全屏）
镜头 zoom      只改精灵大小       scale_steps 盖不住  怪兽确实会变
```

**所以「兼容缩放」仍然要做，只是理由变了**：不再是"金币会检不到"，而是
**扩展到世界空间目标时必然撞上**——怪兽、以及任何不是屏幕空间 UI 的对象。
金币这条路径侥幸不受影响，不代表下一个功能也侥幸。

**第一步不是"兼容缩放"，是"发现缩放并停手"。** 这与「不猜，宁可停」是同一条原则：
容忍缩放是一项独立且不小的工程（模板多尺度或换检测器），
而**发现自己已经离开标定范围**很便宜，数据已经在手上了——

`Detection` 带 `width` / `height`，也就是**每次检出都在报告目标的当前尺寸**。
金币图标标定尺寸是 50x38，所以检出框尺寸的中位数一旦持续偏离 ±3% 带宽，
就说明镜头缩放变了。这个判据不需要新素材、不需要新算法，只需要把已有字段用起来。

**所以「兼容缩放与拖动镜头」这一项的性质变了**：它原来是低优先级的鲁棒性改进，
现在它的**前半段（检测并报警/停手）是安全项**，后半段（真正容忍缩放）仍然可以延后。
前半段应该和误触取证、画面静止门放在同一轮实机里验证——三者是同一个问题的三个面，
分成三轮实机等于把同一件事验三次。

**v1 不因此阻塞**，但 README 必须诚实写明这条已知限制：
当前按固定镜头标定；金币图标是屏幕空间精灵所以缩放不影响识别，
但**缩放会改变可见范围，视野外的金币不会被收集**，所以运行前应把镜头缩到视野最大。
世界空间目标（怪兽等）会随缩放变化，扩展到那些目标时需要先解决缩放。
**把已知限制写清楚是这个仓库的风格，不是它的短板。**

### 第二个有机制的候选解释：物理鼠标指针抢走了悬停目标

**这一条目前是假设，不是结论**，但它是**第一条能解释"第一次误触"的机制**——
前面那条"连续点击被解读成拖拽"只能解释级联，解释不了最初那一下。

**实机观察**：**鼠标指针飞速运动时，误触概率大幅提升。**

点击序列里有一个敞开的窗口：

```python
_send(WM_MOUSEMOVE, lparam)          # 伪造的悬停 → 目标金币
_sleep(pre_press_delay)              # 8~25 ms   ← 竞态窗口
_send(WM_LBUTTONDOWN, lparam)
```

物理鼠标划过游戏窗口时，Windows 会把**真实的 `WM_MOUSEMOVE`** 投给那个窗口，
**且不需要焦点**——后台窗口的悬停效果就是这么生效的。如果游戏按"最后一次移动消息
记录的指针位置"判定命中（而不是用按键消息自带的坐标）：

```
我们 MOVE(金币)    → 游戏内部指针 = 金币
真实鼠标划过       → 游戏内部指针 = 物理光标所在
我们 DOWN(金币)    → 游戏在「物理光标处」点了一下
```

**它与全部既有证据吻合**：识别正确而落点错误、偶发且无法复现（取决于有没有动鼠标）、
落在建筑上导致平移、以及回读把它记成成功（平移让金币移出被检查的 20px 邻域）。

**还有一条内部证据**：`ClickConfig.move_before_click` 存在的理由写着"某些游戏只有
悬停后才响应点击"——**这本身就说明这个游戏在独立跟踪指针位置。**

**判决性实验（预测很尖锐，所以值得先做）**：物理光标不在游戏窗口上时，
游戏收不到任何真实移动消息，伪造的悬停就是权威的，**误触应该基本消失**。

```
A 轮   鼠标移到游戏窗口外，完全不动     跑 2 分钟
B 轮   鼠标在游戏窗口内来回快速划动     跑 2 分钟
```

两轮都读日志里的「抽检 N 次（M 次失败）」与「坐标过期跳过 K 次」。
**A 轮几乎不失败而 B 轮大量失败，机制即成立。**

**如果成立，修法不是缩短那 8~25ms**（两次 `SendMessage` 之间永远有缝），
而是**加一道指针门**：点击前读 `GetCursorPos`，物理光标在客户区内且正在移动就不点。
`GetCursorPos` 是只读的，不移动鼠标，不违反「绝不移动物理鼠标」。
这与 memory game 的结论同形：**不要试图跑得比干扰快，直接测量干扰在不在。**
副作用是正向的——用户手动操作游戏窗口时脚本自动让路。

## 已知未处理：遮挡

钻石／食物牌子会遮挡金币，导致金币检测不到。已知悉，后续再修。
补充说明：其他收集物（钻石、食物）也是「云朵包裹」的形式——
金币牌 = 金币 + 云朵，钻石牌 = 钻石 + 云朵。
